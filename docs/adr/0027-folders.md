# ADR 0027: Folders — one level, Claude files items, the viewer only reads

**TL;DR:** Items can be filed into **one level** of named folders (at most one folder per item, else "unfiled"). Claude creates, renames, deletes folders and moves items (admin API + MCP); the viewer only lists folders and filters by them. A move is an item compare-and-swap; a folder can be deleted only when no item in **any** state references it (SQLite foreign key `ON DELETE RESTRICT` + an explicit check in the same transaction). Names follow the title rules (1..80 chars), are secret-scanned and unique under caseless matching; at most 200 folders.

## Context

- Owner decision (backlog 6, "Approve as proposed"): the feed grows flat; the owner wants Claude to organise items into folders shown as desktop icons.
- Items are already versioned (`updated_at` as a CAS version, ADR 0019) and written by two processes (admin: edits/revisions; viewer: trash/restore/pin, ADR 0020).
- Folder names are untrusted display text written by a prompt-injectable publisher, like titles (C7, C15).

## Decision

- **Model.** `domain/folders.py`: `FolderId` (ULID), `Folder(id, name, created_at, updated_at)` (frozen, validated; name = `sanitize_line(max_chars=80)`, uniqueness key `caseless_key(name)`), `UNFILED` sentinel, `parse_folder_filter`. `Item.folder_id: FolderId | None` (validated); every transition keeps it; only `Item.moved_to(folder_id, at=...)` changes it — allowed in **any** state (organising is not editing content, and it lets Claude empty a folder of trashed items without restoring them; `trashed_at`, hence retention, is untouched).
- **Listing.** `ItemQuery.folder`: None (all), a `FolderId`, or `UNFILED`; same order and cursors. SQLite: `folder_id IS ?` (NULL = unfiled) in four more static list shapes, served by `idx_items_folder_order (folder_id, state, pinned, created_us, id)`.
- **Port.** `FolderRepository`: `add(folder, *, max_folders)` (quota + uniqueness atomic), `get`, `list` (name-key order), `rename(folder, *, expected_updated_at)` (uniqueness atomic, compare-and-swap on `updated_at` like `ItemRepository.save` — `ConflictError` on a stale caller, so two racing renames don't silently pick a last-write-wins winner), `delete_if_empty` (atomic; `ConflictError` if referenced), `counts(state)`. Moving is `ItemRepository.save`, which raises `NotFoundError` if the target folder is missing at commit (explicit check under the write lock; FK as backstop). `FolderService.rename` never retries on `ConflictError` (like `LifecycleService.update`): a new name is a specific intent, not one to reapply blindly.
- **Storage.** Migration 4: `folders (id PK, name, name_key UNIQUE, created_us, updated_us) STRICT`; `items.folder_id REFERENCES folders ON DELETE RESTRICT` (NULL for every existing item = unfiled); rows re-validated on read (a `name_key` that doesn't match its name fails closed). `get` fails closed on that one folder (`ValidationError`); `list`/`counts` must not let one tampered row take down `/api/folders` or an item listing that renders `folder` — `list` skips the bad row (logged by id only) and `counts` is naturally unaffected (it never rebuilds a `Folder`, only correlates ids).
- **Application.** `FolderService`: `create`, `get`, `list(state)` (with counts + unfiled count), `rename` (no-op if unchanged), `delete`, `move(item_id, folder_id | None)` (no-op if unchanged; one re-read + retry on conflict, like trash/restore). Names are scanned raw and sanitized (C15). `PublishCommand.folder_id` files a new item directly (checked before any byte moves; `repo.add` re-checks atomically, rollback deletes the blobs).
- **Capabilities.** Admin core: `FolderService`. Viewer core: `FolderReader` (`list`, `get` only). Purge: nothing — purging an item simply frees its folder; folders are never deleted automatically. Pins stay global.

## Consequences

- New controls C39 (names), C40 (viewer read-only folders), C41 (referential integrity) in `docs/security.md`.
- Viewer and purge refuse to start until the admin has migrated to schema 4 (as for every migration).
- Deleting a folder that still holds trashed items requires moving them out (or waiting for purge); nothing is ever deleted implicitly with a folder.
- Folder ids share the item-id ULID stream (`IdGenerator.new_item_id`), like question/notification ids; the port is unchanged.
- Interfaces (admin/MCP routes, viewer `/api/folders`, `folder` in item JSON) are unit F2; the desktop UI is unit F3.
- S-F1 review fixes (backlog 6.4, unit F-F1): `list`/`counts` degrade gracefully on one tampered folder row instead of raising (F2's `/api/folders` and item listings render `folder: null` for a skipped row, never an error); `rename` gained the same optimistic-concurrency compare-and-swap `save`/`move` already had.
- F2 decisions (backlog 6.2): every item's `folder` JSON is resolved from **one** `FolderLookup` read per response (`interfaces/folder_refs.py`), never a lookup per item; a folder that read misses (deleted concurrently, or a skipped tampered row) renders `folder: null`, never an error. The admin `GET /v1/folders` listing adds `trashed_count` per folder (and `unfiled_trashed_count`) so Claude can see why a `delete` would be refused (C41) without a second call. MCP folder tools are always registered (unlike, say, the notifier tools, which depend on config) — folders have no feature flag. `move` (admin API, MCP, and `FolderService.move`) works on an item in **any** state, including trashed (ADR text above); a trashed item keeps whatever folder it is moved to and returns there on restore.
- S-F2 review fixes (backlog 6.5, unit F-F2): the item `folder` JSON now reads folder names through `FolderReader.names()` / `FolderService.names()` (`FolderRepository.list()` with no `counts()` read), not `list()`, since resolving refs never needs item counts; `interfaces/admin/{folders_api,api}.py` each recheck the token role themselves (`require_admin`, shared with `questions_api.py` from `admin/api.py`) as defense in depth next to `BearerAuthMiddleware`, on every folder route and on `POST /v1/items/{id}/move`. `docs/operations.md`'s folder-upgrade rollback also stops the purge **service** (not only its timer) before touching the WAL files, and documents the reverse-orphan case (a rolled-back row can point at a blob the purge job already removed). No rate limit on folder create/rename/move is an accepted known limitation (`docs/security.md`): admin token only, and the 200-folder quota already bounds `create`.
