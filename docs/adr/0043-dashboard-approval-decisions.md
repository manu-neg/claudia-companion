# ADR 0043: Approve/Deny Claudia's requests on the dashboard

**TL;DR:** The "Waiting for your approval" panel gets Approve (+ authenticator code) and Deny. The viewer only forwards `{request_id, decision, code}` over the admin socket with its own scoped **viewer token** (`/v1/viewer/*`, one route); the admin re-validates everything and checks the code with the same `StepUpService` (shared replay mark, counters, lockout). **On by default** whenever Claudia is on (`claudia_dashboard_decisions = false` turns it off). Unit F-CL6, C46/C47. Owner decisions 2026-11-09.

## Context
- Owner: "It should appear on Telegram and the dashboard and I'll click it on the dashboard."
- Until now the panel was read-only by design (C46 independent check) and the viewer had no path to the admin at all: it masks `/run/preview-dashboard`, holds no admin client, and its only writes go to the shared item DB.
- Viewer-writable stores are untrusted by the admin (ADR 0034): an approval or a code must never travel through them (codes are never stored, C47).

## Decision
- **Channel:** the notifier pattern, not a store. A fourth admin token role `viewer`, accepted only on `/v1/viewer/*` (`POST /v1/viewer/approvals/{id}/decision`), its own peer-uid family (`--viewer-peer-uid`), its own token file (`viewer_token_file`, C12 rules, `TokenKind.VIEWER`). Every other token is refused there and the viewer token everywhere else (403). Synchronous: the owner gets the verdict at once; nothing is written to disk on the way.
- **Viewer side:** `POST /api/claudia/approvals/{id}/decision` behind the full C2–C4 stack (owner identity, Host, fetch metadata, CSRF matrix, 1 KiB body). Strict body (`{"decision":"approve","code":"[0-9]{6}"}` or `{"decision":"deny"}`, no other keys), a 20/10 min click budget (429), and `AdminDecisionClient`, which re-verifies the admin socket (`verify_admin_socket`) before every call and fails closed (503) on any oddity. The code is only in the POST body; never in a URL, log or repr.
- **Admin side:** `DashboardDecisionService` charges its own 20/10 min budget, then: **Deny** = the Telegram Deny CAS (`PENDING/TAPPED → DENIED`); **Approve** = `StepUpService.submit_dashboard_code` under the same lock: lockout → request decidable (exists, PENDING/TAPPED, unexpired, by the admin's clock) → secret → RFC 6238 match after the replay mark → burn step → `PENDING → TAPPED → APPROVED` (one CAS each). Wrong or replayed codes count in the one shared budget and raise the same alert. An undecidable request is reported without checking the code (nothing learned, nothing counted).
- **First decision wins** across both surfaces (every step is the store's CAS); the loser gets `already_decided`. The decision is logged as "decided on the dashboard" (no schema change; the row carries no source).
- After a dashboard decision everything else is unchanged: the F-CL5 resolve edits the Telegram prompt, the snapshot drops the row, the host's poller sees APPROVED/DENIED, consumes and resumes Claudia.
- **UI:** buttons only when `decisions: true` and the row is PENDING/TAPPED; Approve opens an inline 6-digit field, Deny asks to confirm; one fixed text per verdict.
- **Default on (owner, 2026-11-09):** the owner asked to decide on the dashboard, so `claudia_dashboard_decisions` defaults to `true`, but it acts only with `claudia_enabled` (`Settings.dashboard_decisions_active`); with Claudia off no viewer token is read and the admin admits no viewer uid. An explicit `false` turns it off; env may only turn it off; a non-boolean value refuses to start.
- **Deploy:** group `pdash-viewtok` on every host (both static units name it; pdash-admin its only member with `--claudia`), `viewer.token` `root:pdash-viewtok` 0640 (created with `--claudia`). The viewer unit gains `SupplementaryGroups=pdash-viewtok` and `--token-group viewer=pdash-viewtok`, and **drops unit 12's L1 mask on `/run/preview-dashboard` on Claudia hosts only** (the static unit keeps it; `install.sh --claudia` writes the drop-in `preview-dashboard-viewer.service.d/claudia-decisions.conf` that restates `InaccessiblePaths=` without it): it reaches `admin.sock` through its effective group `pdash` (dir 0750, socket 0660), so no ACL is needed (the notifier needs its ACL only because it is not in `pdash`). The admin unit gets `--viewer-peer-uid ${PDASH_VIEWER_UID} --token-group viewer=pdash-viewtok` (from `viewer-uid.env`). `check.sh` checks the token mode, group members, the socket and token from inside the viewer's namespace, the token's scope live, and warns when the units are not wired.

## Consequences
- The panel becomes a decision surface. Its independence argument changes: the panel still shows the admin's own stored text (snapshot), but a compromised viewer could now show one request and submit a code for another open one, or burn the 5-wrong-codes budget (15 min lockout DoS). Both need a valid code for an approval and only affect requests Claudia already asked for; Telegram still shows the real request. Known limitation in security.md.
- Lifting the L1 mask means a compromised viewer can connect to the admin socket again. The admin's peer policy and token scopes are what stop it there: from the viewer's uid only `/v1/viewer/*` is open, and only with `viewer.token`.
- Claudia's host rules and the resume turn now say the owner decides on Telegram or on the dashboard, first decision wins ("Approved by the owner with the authenticator code (Telegram or dashboard): …"). The resume turn does not name the source because none is stored.
