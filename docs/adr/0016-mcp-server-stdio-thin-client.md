# ADR 0016: MCP server — stdio-only `MCPServer`, thin streaming client of the admin API

**TL;DR:** `preview-dashboard-mcp` is an `mcp` 2.x `MCPServer` (the SDK's new name for FastMCP) that only runs over stdio. Its seven `dashboard_*` tools pass local files through the intake policy and then stream them to the admin API over the Unix socket. They return compact JSON text, and every failure comes back as one caller-safe line. The server takes no env and no arguments, and it reads the token file itself.

## Context

- Claude Code starts MCP servers as child processes and talks to them over stdin/stdout. Anything else the process writes to stdout corrupts the protocol. The registration's `env` block is also the easiest input for an injected agent to change (C30).
- The pinned SDK (`mcp>=2.2,<3`) removed `mcp.server.fastmcp` and replaced it with `mcp.server.mcpserver.MCPServer`, which has the same decorator API.
- Publishes can reach `max_item_bytes` (500 MiB). The admin API wants a manifest-first multipart body (ADR 0014).
- The deployed token file is `root:pdash` 0640 (ADR 0017 amendment "G"). The MCP process runs as root, and the shared C12 loader only trusts the groups root and the process's own egid unless it is told otherwise.

## Decision

- **Transport:** `MCPServer.run("stdio")` only, with no HTTP/SSE code path. Logging goes to a stderr handler that is installed before the SDK sets up its own logging, so the SDK's `basicConfig` becomes a no-op. The SDK's stdio transport also points fd 1 at stderr while it serves, so a stray `print` can't corrupt the protocol.
- **Tools:** `dashboard_publish`, `_list`, `_get`, `_update`, `_trash`, `_restore`, `_kinds`. Arguments are pydantic-typed: the ULID pattern for item ids, the kind-name pattern, and length bounds. Results are compact JSON text (not structured output) that an LLM reads directly, and every item carries `viewer_url`.
- **Errors:** `IntakeError` and the typed `AdminClientError`s become `ToolError`s with a short, escaped message. For secret-scan hits that is the rule label and relpath, never the matched bytes. Any other exception gets the SDK's generic `Error executing tool <name>`, and its traceback goes only to stderr.
- **Client:** `AdminClient` is httpx over `HTTPTransport(uds=...)` with `trust_env=False`, explicit timeouts, and a response size cap. The token is sent only as a default header and never appears in `repr`. The item id is validated before any URL is built. A publish is one generator-backed body with an exact `Content-Length`: fields, then the manifest, then each file's part streamed from its intake fd in 64 KiB chunks. The client aborts if a file delivers more or fewer bytes than announced.
- **Startup:** refuse outright if any `PDASH_*` env var other than `PDASH_CONFIG` is set (unit 10b M1 — see "Amendment" below); vet the config file (C16); then `Settings()` (TOML only, since the registration sets no other env); then `IntakePolicy`; then verify the admin socket itself is trustworthy (`interfaces/mcp/admin_socket.verify_admin_socket`, unit 10b M1/G) *before* the token is ever read, let alone sent — its own gid becomes the one extra group trusted on the token file. Any failure exits 1 with one stderr line and no traceback.

## Consequences

- Claude gets precise, fixable errors (for example "rename `100%.txt`" or "secret rule X in `conf.txt`") and never sees stack traces or internals.
- A publish holds about one chunk per file in memory. A file that changes during upload makes the admin roll back, so nothing is half-published.
- The dependency on `mcp` 2.x's API (`MCPServer`, `ToolError`, `Client(server)` for in-process tests) is pinned by the `<3` cap, so a major bump needs a code review.
- MCP logs end up in Claude Code's own log files rather than journald. `docs/security.md` lists this under Known limitations.

## Amendment (unit 10b follow-up: M1, L3, G)

- **"Takes no env" made literal (M1, C30):** `main()` now refuses to start (one stderr line, exit 1) if `os.environ` has *any* `PDASH_*` key other than `PDASH_CONFIG`. `PDASH_CONFIG` is the one deliberate exception: it only selects *which* TOML file `verify_config_file_secure()` vets (C16 — the file must still be root-owned and not group/world-writable), so an attacker without root gains nothing by setting it that they couldn't already get by writing the default path directly, and the whole test suite depends on it to point the real subprocess at a tmp config. A real registration still must carry no env at all, `PDASH_CONFIG` included (`docs/operations.md` "Registering the MCP server") — the code-level exception exists for testability, not because the registration should ever use it.
- **Admin socket verified before the token is ever read (M1, C12):** `interfaces/mcp/admin_socket.verify_admin_socket` checks, in order, that the configured `admin_socket` is a real Unix socket (`lstat`, never a followed symlink), owned by uid 0 or the `pdash-admin` user, sitting in a directory that isn't group/world-writable, and that a live probe connection's `SO_PEERCRED` peer uid is one of the same trusted uids. Only then is its token read and sent. This closes a gap the original design left open: nothing previously stopped the client from happily sending the bearer token to *whatever* happened to be listening at the configured path.
- **Group name no longer hardcoded (G):** the socket's own gid (`os.lstat(admin_socket).st_gid`), read only after the trust checks above pass, is the one extra group `AdminClient.from_settings` trusts on the token file — `ADMIN_SERVICE_GROUP`/`admin_group_gids()` (a `grp.getgrnam("pdash-admin")` lookup) are gone. This is what lets the shared group revert to its ADR-0013-original name, `pdash` (ADR 0017 amendment "G"); the *user* names `pdash-admin`/`pdash-viewer` are unaffected and still named directly in `admin_socket.ADMIN_SERVICE_USER`.
- **Untrusted content marked as data, not instructions (L3):** every tool result nests `title`, `entry_file`, and (for `dashboard_get`/`dashboard_publish` only) `description`/file details under one `"untrusted_item_data"` key, and `_INSTRUCTIONS` plus the `dashboard_list`/`dashboard_get` tool descriptions say so explicitly — content Claude publishes (or reads back) can itself be the product of a prompt injection (`docs/security.md` threat model), so it must never be read as an instruction merely because it arrives inside a tool result. `dashboard_list` results omit `description` entirely (unchanged behavior, now written into the wrapper instead of the top level).
- **Items are updatable (revisions unit, ADR 0019):** an eighth tool, `dashboard_update_content`, reuses `IntakePolicy.collect` plus a new `AdminClient.publish_revision` (same manifest-first streaming, against `POST /v1/items/{id}/revisions`) so Claude can publish new content onto an existing item's id (one stable `viewer_url` across iterations) instead of always creating a new one; `_INSTRUCTIONS` says so, and every summary now carries `revision`.
