## Threat model

**Assets:**
- Published content (images, docs, video — potentially sensitive; this is the whole point of the app).
- The admin bearer token (`/etc/preview-dashboard/admin.token`).
- The SQLite database and blob store on disk.
- The owner's Tailscale identity/session, and the owner's devices/browser (they render untrusted previews).
- The config file (`/etc/preview-dashboard/config.toml`): it defines who the owner is and what intake may read.
- The Telegram bot token (`/etc/preview-dashboard/telegram.token`) and the notifier token (`/etc/preview-dashboard/notifier.token`); question prompts and alert titles, which leave the host (ADR 0021).
- **Claudia companion (ADR 0031):** the `claudia` token (`/etc/preview-dashboard/claudia.token`); the **TOTP secret** (`/etc/preview-dashboard/totp.secret`, read by the admin only, never by Claude); the owner's free-text messages and approval decisions (inbox, approval requests in the DB); the **knowledge base** (`/var/lib/claudia-kb`, Markdown + its own git history: a summary of the owner's work, untrusted as data); her audit log; `reply`/`voice` texts, which leave the host.
- **Logs and backups** — journald output and backup copies of `data_dir` contain (or describe) the same sensitive content and are protected like the originals (C29).

**Actors:**

Holds the `claudia` token: inbox, replies, approval *requests*, never grants (C45) | Admin socket with the `claudia` token; spawns `claude` CLI runs with a host-built allowlist (C51) |

**Classic web/app checklist** (every review covers these, in addition to the threats below): authN/authZ (identity header, Host check, fail closed on missing values, token handling, socket permissions); CSRF on state-changing routes (Origin / `Sec-Fetch-Site` / custom header); XSS (CSP on every response type, preview sandbox, `innerHTML` use, Markdown sanitization, SVG); path traversal, symlinks, NUL/backslash/normalization tricks, bundle manifest lookups; Content-Type sniffing, `Content-Disposition`, zip arcnames; resource limits (file size/count, body size, render caps, disk exhaustion); publish intake (source allowlist, secret denylist, `O_NOFOLLOW`, TOCTOU); SQL injection, unsafe deserialization, subprocess/shell use; secrets in code, logs, errors, git; verbose error leaks; dependency risks and pinning; systemd hardening and file permissions.

**Threats considered** (beyond the classic checklist above):
| Threat | Why it matters | Mitigation |
|---|---|---|
| Ambient tailnet authentication | Tailscale identity is attached to the *device*, not the tab: any site the owner visits can fire requests at the dashboard and they arrive "as the owner". | Strict CSRF matrix (C4), exact Host (C3), no CORS, **no cookies** (I1), JSON-only state changes, read endpoints return nothing cross-origin-readable (CORP/COOP, C22), fetch-metadata resource isolation (C31). |
| Disk / DoS exhaustion | A prompt-injected Claude can publish in a loop; big uploads can fill the disk and take the host down. | Per-file/item limits, global quota (`max_total_bytes`, `max_items`), `publish_rate_per_hour`, free-disk floor, limits enforced on streamed bytes (C18); systemd `MemoryMax`/`TasksMax` (C28). |
| Preview tracking / phishing | Hostile HTML can try to beacon out (tracking pixels, fetch), or render a fake login page that looks like the dashboard. | Preview CSP `default-src 'none'`, `connect-src 'none'`, `form-action 'none'`, sandbox (C5); dashboard CSP blocks remote images (C6); preview lives on a visibly different origin; the dashboard has no login form to imitate. |
| Service worker persistence | A script that manages to register a service worker on the dashboard or preview origin would outlive the page and intercept every later request to that origin (forged UI, forged previews, replayed actions). | Every request carrying `Service-Worker` or `Sec-Fetch-Dest: serviceworker` → 403 on both apps; `worker-src 'none'` in both CSPs; `Service-Worker-Allowed` never sent; sandboxed previews have an opaque origin that cannot register one anyway (C5, C31). |
| Hostile media vs device decoders | Crafted images/video/PDF may target the browser's or OS's decoders on the owner's phone. | Accepted residual risk (same as opening any file); mitigated by serving all item bytes only from the sandboxed preview origin (C5), and by the owner keeping devices updated. |
| Logs and backups as leak paths | Content, filenames, or tokens in logs/backups outlive trash/purge. | Never log contents, tokens, `Authorization`, or query strings; journald only; backups local 0600 (C29). |
| Irreversible deletion by an injected agent | A prompt-injected Claude could `dashboard_trash` many items, then `dashboard_empty_trash`, or prune revisions: permanent data loss. | Owner decision (ADR 0030) accepts it for the owner's own local agent. Admin token only (C43); tool descriptions say PERMANENT and "only when the owner asked"; empty-trash touches only items already trashed, prune never drops the head. Claude runs as root on this host anyway, so this adds no new reach. Not built, possible future owner decision: require an answered `dashboard_ask` id before `dashboard_empty_trash`. |
| Tailscale account compromise | An attacker who owns the Tailscale account *is* the owner to this app. | Out of the app's control: MFA on the Tailscale account, device approval, key expiry (owner actions, ADR 0002). |
| Server-side parsing of untrusted content | Image/PDF/video parsers are a classic RCE surface. | **No server-side decoding or parsing** of published content: MIME comes from the extension, bytes are stored and served opaque (C8). |
| Secrets published by an injected agent | Claude runs as root, so intake checks alone can't stop a determined injected agent. | Content secret scan in the admin process on all bytes (C15, ADR 0008); intake policy (C10) as the first, advisory layer. |
| Alerts as a spam, phishing or exfiltration channel | A prompt-injected Claude could flood the owner's phone, send look-alike links, or push secrets out through question text. | One shared 20/hour alert budget, every attempt counted (C37); no web address in any alert text (rejected in the domain, defanged again by the channel) and only a server-built dashboard link (C35); every question names its (self-reported) session (C35); all outgoing text secret-scanned raw and sanitized (C35). |
| Claude answering its own question | An injected agent holding the admin token could pick the option it wants. | Answers only via the notifier token's route; the admin token (the only one the MCP server loads) is never accepted there, and no MCP tool or admin route can answer (C34). **Advisory** against a capable injected agent: Claude runs as root and could read the notifier token itself (see Known limitations). |
| Forged or replayed button taps | Anyone who can message the bot, or a compromised notifier, could try to answer. | Owner chat id match in the adapter; the admin re-validates every tap: OPEN, offered key, first answer wins, unknown → `unknown` (C34). |
| Telegram account takeover = free text (ADR 0031) | Before, a stolen Telegram account could only pick offered options; now its text is Claudia's user turn (D5), a root Claude run. | Owner-only acceptance (C44); screening, flagged = content until a code (C48); the fixed risky set is hook-denied without a consumed Approve + TOTP approval for the same action kind + target (C46, C47, C59); `/stop` kill switch (C58); owner: Telegram 2FA. **Residual (owner-accepted, "risky-only"):** unflagged normal work needs no code (see Known limitations). |
| Prompt injection via forwarded or pasted text | The owner forwards a message or pastes a page; its instructions arrive as the owner's own turn. | Forwarded flag kept by the notifier (C44) → always flagged; parser + strict Haiku (C48); flagged turns run with the read-only tool set until the owner sends a code (C48, C51). |
| Prompt injection via KB notes | Notes are written from model output and re-read at every window start (`index.md`, `now.md`). | Notes are data and record their source; host KB writer: caps, fixed layout, secret scan (C53); gardener confined to the KB (C54); viewer renders them as untrusted (C57). Advisory: the model still reads them. |
| Prompt injection via peer transcripts | Other sessions' transcripts and replies can contain anything (web pages, tool output, secrets). | Treated as untrusted data, never approvals; every peer message audited and prefixed, interactive sessions only after owner confirmation (C52). |
| Approval replay / confusion | A tap or code reused for another action, an old approval resumed, or a misleading action text. | Request bound to one action text + structured action (kind + target) + id, single use (CAS consume), 24 h expiry (F-CL3; legacy rows 600 s), tap only via the notifier token, code only via admin TOTP with no replay (C46, C47); resume text built by the host from the stored request, resume-turn look-alikes in owner text flagged (C46, C48); the hook only lets through the tool call matching the consumed action (C59); the owner reads the exact action text before tapping, and can cross-check it in the viewer (C46). |
| Reply / voice as exfiltration channel | Claudia's replies are long (≤ 4096) and voice audio can't be scanned. | `reply` text sanitized + secret-scanned like C35, no caller links; voice synthesized **only** from the already-scanned reply text, length-capped (C56); her own Telegram tools disallowed (C51). |
| Claudia acting outside the owner's intent | An injected Claudia can label a risky step as normal, or keep acting after a guard block. | The permission guard stays on (auto mode); guard block → stop + `failed`, never retry/reword (C55); approvals (C46) enforced for the fixed risky set by the host's PreToolUse hook (C59, C60); tool allowlist (C51); project memory and settings deny rules (C50); audit log (C52). **Advisory** against a capable injected agent (root, Known limitations). |

**Trust boundaries:**
1. **Tailnet ↔ viewer app** — crossed only by an authenticated Tailscale connection; the app additionally checks the forwarded identity header.
2. **Local host ↔ admin API** — crossed only via the Unix socket (filesystem permissions) plus a bearer token; never networked.
3. **MCP intake ↔ host filesystem** — crossed only for files under an explicit allowlist, filtered through a secret-pattern denylist; the admin API itself never accepts filesystem paths, only bytes. Advisory while Claude runs as root (see Known limitations); the enforcing layer is the admin-side content scan (C15).
4. **Preview content ↔ dashboard UI** — untrusted rendered content (HTML/SVG/raw) is confined to a separate origin with a sandboxed CSP, so it cannot script the dashboard origin even if it's hostile.
5. **Notifier ↔ admin API** — crossed only via the admin socket with the notifier token, which is accepted on `/notifier/*` alone; the admin token is never accepted there (C33, C34).
6. **Notifier ↔ Telegram** — outbound HTTPS only (C38); text out is scanned and sanitized (C35), taps in are untrusted until the admin validates them (C34).
7. **Claudia host ↔ admin API** — crossed only via the admin socket with the `claudia` token, accepted on `/v1/claudia/*` alone: read the inbox, send replies, *request* approvals and read their state; it can never answer questions, record taps, verify codes or grant an approval (C45, C46).
8. **Owner text ↔ Claudia's runs** — every owner message is untrusted until screened (C48); the host, not the model, decides the tool set of each run (C51) and builds every approval resume turn (C46).
9. **Viewer ↔ knowledge base** — one extra read-only root (`ReadOnlyPaths`), `.md` files only, fd-confined walk, size caps; notes rendered as untrusted (I2/I4 amendments, C57).

## Invariants

Hard rules every unit must keep true. A change that breaks one is a security bug, whatever else it fixes.

| # | Invariant | Enforced by |
|---|---|---|
| I1 | **No cookies anywhere.** No process sets, reads, or depends on a cookie; no session state in the browser beyond the Tailscale identity. (Cookies would make ambient-authority attacks worse and leak across ports on the same host.) | C19 |
| I2 | **The dashboard (viewer + preview apps) can never read or list anything outside its own data directory**, with exactly **one** amendment (ADR 0031): the dashboard app may **read** the knowledge-base root (`/var/lib/claudia-kb`, systemd `ReadOnlyPaths`, never writable) — regular `.md` files only, walked fd-relative with no symlinks, no traversal, no hidden entries (`.git` never read), and per-file/total/count caps; the OS grant (`ReadOnlyPaths`) covers the **whole viewer service, i.e. both apps**; only the route table separates them: the dashboard app has the KB routes, the preview app has none (tested, C57). No request parameter is ever used as a filesystem path (a note is requested by the id the server's own walk assigned), and there are **no directory-listing endpoints** (the knowledge-map graph lists only the notes that passed those filters, never raw directory contents). | C20, C57 |
| I3 | **The admin API receives bytes, never paths.** Only the MCP intake reads the host filesystem, and only under the allowlist. | C10, C26 |
| I4 | **No server-side parsing of published content.** Bytes are stored and served opaque; type comes from the extension via the kind registry. One amendment (ADR 0031): knowledge-base notes (not published content) are scanned server-side by a **bounded stdlib parser** that extracts only `[[links]]` and frontmatter `tags`/`updated` (size- and count-capped input, no YAML/Markdown library, no HTML rendering on the server); note bodies are returned as text and rendered client-side as untrusted (C23, C57). | C8, C57 |
| I5 | **Nothing listens beyond loopback / the admin Unix socket**, and only `tailscaled` (root) may connect to the viewer's loopback ports. | C1, C14 |
| I6 | **Fail closed.** Missing/invalid config, unmatched identity, ambiguous input → reject or refuse to start. An explicitly named config file (`PDASH_CONFIG`) that is missing refuses to start instead of falling back to defaults (`bootstrap.verify_config`, F-MCP). | C2, C16, C17 |

## Intake denylist semantics

The pure matcher is `interfaces/mcp/denylist.py` (`DenyList`, unit 10a); these semantics are the contract. It is applied to the resolved root's components and to every component walked below it.

| Rule | Meaning |
|---|---|
| Normalization | Both patterns and path components are compared after Unicode **NFC** normalization and **casefolding** (`.SSH` and `.Ssh` match `.ssh`; NFC, not NFKC, so compatibility look-alikes are *not* folded — the allowlist, not the denylist, is the primary control). Patterns are stored normalized in `Settings`. |
| Unit of matching | Each **resolved path component** (every directory on the walk *and* the final file name) is matched independently with `fnmatch`-style globbing (`*`, `?`, `[...]`), whole-component (`id_*` matches `id_rsa`, not `my_id_rsa`). A match anywhere on the path rejects the file. |
| `(full)` patterns | A pattern containing `/` (e.g. `.config/gh`, `.config/gcloud`, `.config/google-chrome`) is **multi-segment**: it matches when its segments equal a run of consecutive components of the full resolved path (each segment globbed as above). |
| Floor | The built-in list (`DEFAULT_INTAKE_DENIED_PATTERNS` in `config.py`) can never be removed; TOML/env/kwargs can only add patterns. |
| Validity | Patterns must be non-empty, contain no NUL, not start or end with `/`, and contain no `..` segment. |
| Known false positives (by design) | The list is deliberately broad; harmless names are refused too and must be renamed or copied under another name: public keys `id_*.pub` (`id_*`), templates `.env.example` / `.env.sample` (`.env.*`), docs like `secrets-howto.md` (`*secret*.*`), any `token.json`, `.gitconfig`, `*.asc` signatures, `*.sqlite*` files. There is no per-request override (an injected agent would use it). |

Built-in patterns — directories: `.ssh .gnupg .aws .azure .gcloud gcloud .kube .docker .git .hg .svn .claude .config/gh .config/gcloud .password-store .terraform .vault* preview-dashboard .mozilla .config/google-chrome keyrings .config/rclone .config/op`; files: `.env .env.* *.env .envrc *.pem *.key *.p12 *.pfx *.jks *.keystore *.ovpn *.gpg *.asc *.kdbx id_* *_rsa *_ed25519 *_ecdsa authorized_keys known_hosts *.token .vault-token credentials* .credentials* .git-credentials .netrc _netrc .pgpass .my.cnf .npmrc .pypirc .yarnrc* .claude.json kubeconfig *.tfstate* *.tfvars secret* *secret*.* .htpasswd shadow gshadow .*_history *.sqlite* Cookies "Login Data" *.ppk *.p8 *service*account*.json token.json .dockercfg .s3cfg .boto .terraformrc terraform.rc rclone.conf .gitconfig ssh_host_* shadow* gshadow* sudoers*`.

## Env narrowing

Env vars (`PDASH_*`) are the easiest input for an injected agent to influence (e.g. an MCP registration's `env`), so they may only **tighten** security-relevant settings (C17). Base = the TOML value if set, else the default. Violations make `Settings()` raise (process refuses to start).

| Setting | Env may… |
|---|---|
| `intake_allowed_roots` | only list roots equal to or under a base root |
| `intake_denied_patterns` | only add: env ∪ TOML ∪ built-ins |
| `max_files`, `max_file_bytes`, `max_item_bytes`, `max_total_bytes`, `max_items`, `publish_rate_per_hour`, `render_cap_bytes`, `publish_timeout_seconds` | only lower (≤ base) |
| `min_free_disk_bytes`, `orphan_grace_seconds` | only raise (≥ base) |

Constructor kwargs (trusted code: `bootstrap.py`, tests) are not narrowed. `PDASH_CONFIG` selects the TOML file itself, which is why that file must pass C16 before it is trusted; C30 keeps intake env vars out of the MCP registration entirely.

## Known limitations

- **A flagged message can steer non-risky work (F-CL8, ADR 0044).** A flag no longer downgrades the tool set, so on a flagged (or unscreened) message non-risky tools such as Write, Edit, non-risky Bash and dashboard publishing run without approval, exactly as on an unflagged one. Every risky kind (C59) still needs a consumed Approve + code approval; the fixed extra-care line is guidance, not a control. Owner decision 2026-11-09.

- **Dashboard decisions trust the viewer process with a code (F-CL6, ADR 0043).** With `claudia_dashboard_decisions` on, the owner types the authenticator code into the viewer page. A compromised viewer process (or hostile code running on the dashboard origin despite C6) could submit that code for **another** open request than the one shown, or burn the shared wrong-code budget (5 / 15 min → codes locked on Telegram too, a DoS). It can't approve anything without a fresh valid code, can only touch requests Claudia already asked for (≤ 3 open), and Telegram still shows the real request and the F-CL5 outcome edit. On by default with Claudia (owner decision); `claudia_dashboard_decisions = false` keeps decisions on Telegram only. To make it work, the viewer unit no longer masks `/run/preview-dashboard` (unit 12's L1). A compromised viewer can therefore connect to the admin socket, but from its uid the admin opens only `/v1/viewer/*`, and only with `viewer.token` (C4 peer families, token scopes).
- **A compromised viewer can redirect or hide an approval prompt's outcome edit (C46, F-CL5).** The message that gets edited is chosen by the prompt SEND's `message_ref`, which lives in the viewer-writable outbox. A compromised viewer can therefore make the edit hit another message or none. Availability and labelling only: no approval is granted, and the viewer panel remains the independent check.
- **Root on this host can forge local requests.** A process running as root can bind wherever it likes, read the admin token, or connect to loopback and fabricate the `Tailscale-User-Login` header (C14 deliberately allows uid 0, because `tailscaled` is root). Accepted as out of scope: if an attacker already has root, the dashboard is not the weakest link.
- **Any local user can reach loopback TCP by default, and `tailscale serve` self-attributes local connections to the owner.** Loopback binding (C1) alone does *not* restrict which local users can connect; without C14 any non-root local process could forge the identity header directly against 127.0.0.1:8787/8788. Separately, `tailscale serve` treats a connection this host makes to *its own* tailnet address on 443/8443 as coming from the host's owner (the same self-attribution `tailscale serve` uses to let the operator curl their own service without a client cert) — so a non-root local process could reach the exact same effect by connecting to `https://<host>.ts.net` (or `:8443`) instead of the loopback port directly. C14's nftables rule gates both: `meta skuid 0` on `oif lo` dports 8787/8788, and (unit 12 audit, High 1) `fib daddr type local` on dports 443/8443, ordered after the loopback rules in the same table — only root (`tailscaled`) may originate either kind of connection. Live-verified by `deploy/check.sh` (a `nobody` process is refused on all four ports). Tagging the host `tag:pdash` and scoping the tailnet ACL grant to it (`deploy/tailscale/acl-snippet.json`) is an optional extra layer on top of this — it restricts which *other* tailnet devices may reach the host at all, but does nothing about a local process on the host itself, which is what C14 defends against.
- **Claude runs as root, so MCP intake (C10/C27) is advisory.** A capable prompt-injected agent can bypass the MCP server entirely (read files itself, call the admin API with the token it can read). Intake stops accidental and naive exfiltration; the enforcing layer against publishing secrets is the admin-side content scan (C15, ADR 0008), which is itself best-effort pattern matching (it will not catch encoded, split, or novel-format secrets — see the next item). Running the MCP server as a dedicated non-root user (C27) would make intake OS-enforced.
- **The content scan (C15) only sees plain ASCII/UTF-8 renderings of a secret.** It does not decode anything, so these pass: UTF-16/UTF-32 text (NUL-interleaved bytes), base64 / base32 / hex encodings, gzip/zip/other compressed or encrypted payloads (incl. inside PDFs, images, archives), percent-encoding (`%41KIA…`), HTML/XML entities (`&#65;KIA…`), JSON/JS `\uXXXX` escapes, tokens split by markup or whitespace inside **file content** (only title/description are sanitized before scanning), and JWTs whose header segment exceeds 4096 or payload 8192 base64url chars (bounded for ReDoS safety). Decoding would mean server-side parsing of untrusted content (explicitly avoided) and an unbounded rule space; the scan is a tripwire against naive/accidental exfiltration, not a DLP system.
- **Publish rate limit and quota reservations are in-process.** They assume a single admin process (the design); a restart resets the rate window. Committed usage (`ItemRepository.usage()`) still bounds the quotas across restarts.
- **No rate limit on folder create/rename/move (ADR 0027).** Unlike publish (C18), these admin-only routes/tools have no `SlidingWindowRateLimiter`. Accepted: only the admin token can call them (C33), and the 200-folder quota (C39) already bounds `create`; a compromised admin token is a bigger problem than a burst of renames or moves.
- **Browsers without fetch metadata** (Safari < 16.4, some native media stacks) get no C31 layer: CSP sandbox, CORP, `frame-ancestors` and CSRF still apply. On such browsers trash/restore don't work at all (the CSRF check requires `Sec-Fetch-Site: same-origin`, fail closed).
- **Pre-app HTTP errors** (malformed request lines/headers rejected by uvicorn's h11 parser before any middleware) are bare 400s without our CSP/security headers. They contain no content and no item bytes.
- **Viewer connection exhaustion → uvicorn's bare 503.** Past `limit_concurrency` (64 per viewer app) uvicorn itself answers `503 Service Unavailable` (plain text, no CSP/security headers, no content) before any middleware or identity check. The header deadline (C21) frees idle/partial-header slots within 10 s and idle keep-alive ones within 5 s, but anything that can reach the loopback ports (via `tailscale serve`, or a local process until C14 is deployed) can keep reopening connections or hold slow downloads open; there is no per-client cap (it would need a custom accept loop). Availability only: no data is exposed.
- **HTML bundles rely on the `Referer` their own pages send** (ADR 0012 amendment). A browser or extension that strips it breaks bundle sub-resources (403 / blocked by CORP) — fail closed; to be verified in real browsers in unit 12.
- **The `latest` revision alias can mix revisions within one bundle page.** A page loaded as `/i/<id>/latest/index.html` loads its sub-resources through `latest` too; if a new revision is published in between, they come from the new revision. The dashboard never uses the alias (its URLs name a revision number); the binding (C31) still keeps every load inside the same item. ADR 0019.
- **Revisions don't share blobs.** Every revision stores all of its files again, so 20 revisions of a large bundle cost 20× its size against `max_total_bytes` (C18); deduplication would need shared, reference-counted blobs (ADR 0019).
- **MCP server logs live outside journald.** Claude Code captures the stdio server's stderr in its own logs, so C29's "journald only" does not cover them; they carry no token or file contents (C29 test); tool-error text (refused file names) is kept out since F-MCP, but startup failures still name the offending config/socket/token path.
- **Admin socket group members can still exhaust connections.** The header deadline (C26) frees a pinned slot within 10 s, but a local process in the socket's group that keeps reopening connections can hold `limit_concurrency` (32) slots continuously and cause 503s before authentication. Only the admin/MCP users should be in that group (C26/C28); a per-peer connection cap would need a custom accept loop.
- **Owner-accepted risk "risky-only" (Telegram 2026-11-08): no authenticator code at window start.** Whoever holds the owner's Telegram account can answer open questions (one of the offered options only; ADR 0021) **and, with Claudia (ADR 0031), start normal (non-risky) root Claude work by free text**, without a code unless the screen flags it. The fixed risky set is blocked by the hook without a consumed approval (C59, C60) and flagged messages need one (C48); risky-looking steps **outside** that set are judged only by Claudia (the model) and the permission guard. A compromised notifier can forge owner text the same way (C44), but not codes. Owner mitigation: Telegram 2FA; plus the screen, the guard, `/stop` and the audit log.
- **A compromised notifier can relabel what the phone shows.** It can show a different action text next to a real request's buttons, so a tap + code may approve something other than what the owner read; TOTP proves the owner's **presence, not intent**. Mitigation: pending approvals (text, action kind + target, id) are listed read-only in the viewer, outside Telegram (C46); check there before sending a code for anything important.
- **The risky-action hook is a classifier, not a sandbox** (C59): inline code (`python -c`, `bash -c`, `eval`) is `unknown`, but a risky step hidden from it is not seen: a script written to disk and then run; a git or gh alias, git hook or `core.*` command written into a config file with the editor tools (`~/.gitconfig`, `.git/config`, `.git/hooks/`, `~/.config/gh/`); a program named by a non-literal word (`chronic "$P" …`) or reached through a command in the no-exec list; files written by a program it doesn't model (only the writers listed in C59 are checked); such steps fall back to Claudia and the permission guard.
- **Closed lists in the classifier** (C59): the stripped wrappers, the opaque runners, the modelled writers and the "never runs its arguments" list are fixed sets; a new wrapper-like tool is caught only if a literal word names a risky program. Fail-closed costs: `tar -x`, `unzip`, `cp -r` or `rsync` into her cwd and writes into a `.claude` dir by unknown name are denied without an approvable target (extract into a sub-dir instead); every use of `ssh`, `tmux`, `at` etc. is `unknown`.
- **The hook pin is taken at host start and covers source files only** (C59): the hook script and the package files it imports (`preview_dashboard/__init__.py`, `interfaces/__init__.py`, `interfaces/claudia/{__init__,hook}.py`) are compared with a SHA-256 before every run; a change made before the host started, byte-code caches (`__pycache__`), `.pth` / `sitecustomize` start-up files and the interpreter's stdlib are not pinned (owner and mode checks still apply to the hook and its interpreter). Its allow decisions also depend on Claude Code honouring `PreToolUse` hooks in `-p --resume` (re-verified on upgrades, C60).
- **Claude and Claudia run as root, so TOTP, the tool allowlist, the hook and the deny rules are advisory against a capable injected agent** (C47, C50, C51, C59): a run with Bash could read `totp.secret` or the tokens, write project memory or the KB directly, or call admin routes itself. They stop every naive path and keep each step visible (approval texts on the phone, audit log, KB git history); running Claude as non-root would make them enforcing.
- **An approval binds the action text and one structured action, not every tool call.** The hook lets through only risky calls matching the approved kind + target (C59), but other, non-risky calls in the resumed turn are not limited (V1: the resume counted as user input). The owner must read the action text and target; misleading text from an injected Claudia is the residual risk.
- **Peer-message rules are preventive only while hooks fire for `SendMessage`** (C60); the transcript audit (C52) is the detective backstop, and if the M4 check fails `SendMessage` is replaced by a host-owned tool.
- **Owner decision (F-CL3, 2026-11-09): Claudia messages sessions the owner is attached to without a code** (C52, C60). The only check is the exact prefix (so the owner sees who wrote); the receiving session treats it as a peer turn (never an approval) and the permission guard still judges whatever it does next. An injected Claudia can still put misleading text into an owner-attached session.
- **24 h stale-approval risk (F-CL3, C46).** An open request now lives 24 h and outlives its window, so the owner may approve something asked hours ago in a conversation that has moved on. The resume turn restates the stored action text + target, the cover is that exact action only (single use, one run), Approve still needs the tap + TOTP code, and `/stop` cancels every open request; read the action text and target before approving an old one.
- **Parked requests live in the host's memory; a restart cancels them** (F-CL3, F-CL3b): the host forgets which requests it is watching, so at start (and at shutdown and `/stop`) it cancels **every** open request of every window through the admin (`POST /v1/claudia/approvals/cancel-open` with `{}`), logging the count; otherwise a lost request would hold the 3-request open cap for 24 h and an approval of it would never be consumed. **The owner must ask again after a host restart or deploy** (an approval tapped just before it is cancelled too). If the cancel call fails, one `failed` alert is sent and the requests expire on their own (24 h). Nothing runs without the host consuming a request.
- **`request_approval` is tied to the run by a nonce, not authenticated** (F-CL3b, C46): the host puts a fresh random token in the run's `claude` child env (`CLAUDIA_RUN_NONCE`) and the tool must present it on the root-only control socket; it stops a stray process (or an old run's server) from opening requests while another run is active, but the run itself, which is root and can read its own env, can still call the socket. The request text/kind/target checks and the owner's Approve + code are the real gates. Claude Code must pass its env to stdio MCP servers (verify at deploy; if it does not, the tool refuses and she falls back to the reply-line request).
- **Guard behaviour depends on Claude Code 2.1.x** (V1, V5, checked on 2.1.319): how `-p` prompts, resumed turns and peer messages count for the auto-mode guard, the transcript format (C52) and `permission_denials` (C55) are internals; re-verify V1/V5 on every Claude Code upgrade before restarting the host.
- **The hook is advisory while Claude runs as root** (C59): a capable injected agent can edit what the deny rules don't cover or run steps the classifier can't see; the permission guard still decides every call the hook leaves open (the hook never allows).
- **`curl -o` / `wget -O` file writes are unclassified** (C59): the classifier flags mutating HTTP calls to GitHub, not downloads that write files; such a write is judged only by Claudia and the guard.
- **The broad-allow check is a heuristic** (C59, hook-8): a rule for a program that runs other programs but is not in the shell / interpreter / wrapper / opaque lists (`Bash(make:*)`, `Bash(uv run:*)`, `Bash(npx:*)`) still passes the preflight; the hook still sees every call those rules let through.
- **The gardener holds the full admin token** (C54): it publishes its summary and `done` alert with `admin.token`. The model it runs has only the KB tool and the unit masks hide every other secret, so it can't reach the token; a scoped gardener token is a follow-up.
- **The code-message delete-retry queue is in memory** (C47): a notifier restart forgets pending retries (the code message stays in the chat until the owner deletes it); the 47 h limit and the fixed notice still apply to what it remembers.
- **Runs are root:** a run can deliberately move a process out of its cgroup (ADR 0039), so `/stop` is not a guarantee against a hostile run.
- **Live checks at deploy are still open** (C59, C60, C58): hook `session_id` equals the window id under `--resume`; hooks fire for `SendMessage` and inside subagents; background-job containment (ADR 0039). Until done, treat those layers as unverified on the real Claude Code build.
- **The Haiku screen is itself a model** reading the hostile text; it can be talked into `ok`. The parser runs first and a hit always flags (OR), but a novel phrasing that passes both reaches Claudia as the owner's turn.
- **Claude runs as root, so "the admin token can never answer" is advisory** like MCP intake (C10): a capable injected agent could read `notifier.token` and call `/notifier/answers` directly. It stops every naive path (no tool, route or admin-token call answers), and each question still shows on the owner's phone; running Claude as non-root would make it enforcing.
- **Telegram sees alert text** (prompts, labels, session labels, titles, dashboard links) and, with Claudia, the owner's messages, her replies and voice audio (C56), so conversation content does leave the host. Only scanned, sanitized fields are sent (C35, C56); never item files, though a reply may summarize them.
- **Notifier admin-socket access depends on POSIX ACLs (the `acl` package).** `pdash-notify` is deliberately not a member of `pdash` (C33), so its ability to reach the admin socket at all comes from two ACL entries the admin unit's `ExecStartPost` sets on its own `RuntimeDirectory`/socket, not from any group. `install.sh` refuses to install the notifier while `setfacl` is missing (installing `acl` is an explicit owner step). Should `setfacl` still vanish later, or `/run` (normally tmpfs) have ACLs disabled, the grant step logs why to the admin unit's journal but never fails the admin unit; the notifier then fails closed with a `verify_admin_socket` refusal, and `deploy/check.sh` fails its "pdash-notify can open the admin socket" row.
- **The session label is self-reported.** Every alert names the asking session (C35), but the caller chooses the label, so an injected agent can claim to be another session; it only helps the owner spot a question out of context.
- **A SEND for an already-resolved question is settled unsent** (outbox `pending`). If the notifier crashes after posting an alert but before reporting it, and the question is resolved meanwhile, the posted message keeps its buttons; a late tap still gets `already_answered`/`expired`/`cancelled` (C34).
- **Alerts are given up after 8 failed tries (~1.5 h)**; a question whose alert never arrived still expires normally and can be waited on via the CLI. The alert rate limit is in-process like C18's (a restart resets the window).
- **Housekeeping removes notifications older than 30 days with their pending deliveries.** A question that expires only when the purge job first runs more than 30 days after it was asked (the job down for weeks) keeps its buttons on Telegram; a late tap is answered `expired`.
- **Hostile media** can still target decoders on the owner's devices (see Threats); no server-side mitigation beyond origin isolation.
- **Owner voice notes and photos (C62).** (0) *On by default (owner 2026-11-09):* with `claudia_enabled`, both inputs are accepted unless set to `false`, so new attack surface (image text, audio parsers) is live without an extra opt-in. (1) *Prompt injection in images:* a photo can carry text the model reads. Read-only turns (the default) cannot change anything; with `claudia_photo_turn_tools = full`, text in an image can steer a turn's actions; the fixed framing, the C59 hook and approvals still apply, but that is the owner's open choice. (2) *Transcription mistakes:* whisper `base` can mishear, and a misheard note is screened and run like typed text. The `(transcribed voice note)` marker tells Claudia, and risky steps still need Approve + code. (3) *Decoder CVEs:* libsndfile 1.2.2 has open CVEs (WAV/AIFF/MAT4/MPEG parsers) and the whisper.cpp audio CVEs (CVE-2025-14569, CVE-2026-17512) are not confirmed fixed. Mitigation: the Ogg/Opus content check runs before any decoder, decoding happens only inside the network-less dynamic-user sandbox, and whisper-cli only reads a host-checked canonical WAV. Not a fix, a containment. (4) *Live checks:* the sandbox properties come from the S0 spike; the extra hardening properties and the bind targets under the private `/tmp` are first exercised at deploy. A `/stop` does not cut a transcription short (≤ 135 s); the message is then dropped. A photo is gone before any later approval resume turn.
- **Text inside a photo outlives the file (C62).** What the model read from an image stays in that window's `--resume` context for later turns of the same window, even after a read-only photo turn; `/new` ends it. Treat later turns of that window as having seen the image's text.
- **Image decoding by Claude Code (C62).** Claude Code's Read tool may decode the JPEG outside any sandbox of ours. The risk is reduced because Telegram re-encodes `photo` uploads (not documents, which are refused, C61) and the walker strips metadata and trailing bytes; it is not removed.
- **Tailscale account compromise** equals owner compromise; mitigated only by the owner's account security (MFA, ADR 0002).
- **MCP admin-socket/token trust depends on NSS for one name (`pdash-admin`).** `interfaces/mcp/admin_socket.verify_admin_socket` no longer looks up any *group* by name (C12/C28, ADR 0017 "G"), but it still resolves the `pdash-admin` **user** (`pwd.getpwnam`) to widen its trusted-uid set beyond root; that lookup goes through NSS (`/etc/passwd` or a configured directory service). If NSS is unavailable or misconfigured, the lookup fails closed (`KeyError` → treated as "the user doesn't exist", so only uid 0 is trusted) rather than open, but a slow or hung NSS backend (e.g. LDAP) on the lookup path would add to MCP startup latency. Group *membership* in `/etc/group` is never consulted anywhere in this trust path (systemd's `Group=` sets the real/effective gid directly, ADR 0017 #2).
